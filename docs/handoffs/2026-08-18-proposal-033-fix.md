## The failure

`tests/test_forge_shadow_eval.py::test_no_skip_reason_argument_is_left_unresolved`
failed on `weather_bracket_width_matched.py:432`:

```python
if estimate is None:
    return decide('SKIP', estimate_status, **estimate_feats)
```

`tests/skip_reason_ast.py` resolves `decide('SKIP', ...)` call sites by
static analysis; a variable is only resolvable if the resolver can find the
producing function and read its `return` statements. `estimate_status`
comes from `self._model.daily_extreme_estimate(...)`, a **method defined in
a different module** (`weather_arb.py`'s `WeatherArb` class). The resolver's
`_producer()` only looks up `func.attr` inside the CALLING module's own
`functions`/`classes` registry (or a direct `from x import y`) - it has no
cross-module instance-attribute type inference, so it correctly reports
this as unresolved rather than guessing.

Note this is the exact same shape as `weather_arb.py:4060-4067`, which
calls the *same* method and forwards the *same* variable - and that call
site resolves fine, because there `daily_extreme_estimate` is a method of a
class defined in the *same* file the resolver is walking. The bug is purely
about which module the method's `def` lives in relative to the call site,
not about anything wrong with the method itself.

## Fix chosen: (b), not (a) - enumerate, don't collapse

I built option (a) first (one stable literal
`daily_extreme_estimate_unavailable`, with `estimate_status` kept as a
feature), following the file's own `airport_reading_unavailable` /
`source_reporting_precision_unknown` precedent (same file, same shape:
status from another call collapsed to one name with the real value kept as
a feature).

**That broke an existing test.** Proposal 033's own test suite
(`tests/test_weather_bracket_width_matched.py`) already has
`test_estimate_failure_propagates_as_its_own_named_status`, which asserts
`FakeForecastFeed(status='feed_network_failure')` produces
`d.reason == 'station_forecast_unavailable'` - i.e. the SPECIFIC status
name, not a generic one. That test's own docstring says so explicitly: "a
`daily_extreme_estimate` failure reaches `evaluate` under ITS OWN status
string, not a generic one." This is the same contract
`WeatherArb.evaluate` already honors for this identical call
(`weather_arb.py:4064-4067`, same comment: "`estimate_status` IS the reason
string, never a shared 'could not price it'").

So (a) was wrong here even though the file has other (a)-shaped call
sites - the test is a signal that THIS particular status needs to stay
distinguishable at the read side (convention 20), unlike `airport_feed`'s
detail. I did not touch the test; it reflects the intended contract.

**Final fix**: an explicit `if estimate_status == '<literal>': return
decide('SKIP', '<same literal>', **estimate_feats)` chain over all 10
known values, plus a defensive fallback branch
(`daily_extreme_estimate_status_unmapped`) for the case where
`daily_extreme_estimate`'s closed set grows without a matching branch
being added here - a cannot-run per convention 11, not a silent merge into
whichever branch happened to be last. Every `decide('SKIP', ...)` call site
now passes a literal, so the resolver is happy and the propagation test
still passes each status through under its own name.

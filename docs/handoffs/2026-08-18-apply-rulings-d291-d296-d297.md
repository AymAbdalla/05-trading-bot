## Task 2: D-296 — the kill clock. **I hit a duplicate definition and removed mine.**

### The collision, exactly

I added `KILL_CLOCK_DAYS`, `KillClock`, `kill_clock_from_rows`,
`kill_clock_from_window`, `liquidation_rows_to_date` and `kill_clock_status`
at line ~749 of `near_liq_trigger.py`. While I was doing it, 55490 added
`KILL_CLOCK_DAYS`, `liquidation_row_count` and `kill_clock_status` at line
~1220 of the same file.

**Python does not error on this.** Two module-level `def`s of one name means
the later one silently wins — the same failure shape as the duplicate dict key
in `SKIP_CLASSIFICATION` last session, and this time with a function. Their
`kill_clock_status` shadowed mine, and their `KILL_CLOCK_DAYS = 30` (int)
shadowed my `30.0` (float). Nothing would have gone red.

**Resolution: I deleted my entire block.** Theirs is the better implementation —
it evaluates the whole clause (days elapsed from the oldest liquidation row,
entry count, a `fired`/`evaluated` tri-state) where mine only answered
"deferred or not". One name, one site (convention 23).

### What I kept: the guard has to reach the ROW

`kill_clock_status()` is what an **evaluator** calls. But the evaluator runs
weeks later against a log, and it computes the answer against **today's** tape.
A month of rows written while the tape was empty would silently inherit a clock
that started afterwards. So the row has to say it itself.

Added `kill_clock_row_features(window)` at the bottom of `near_liq_trigger.py`,
wired at line 957, **above** the `if not window.ok` early return:

```python
feats.update(window.features())
feats.update(kill_clock_row_features(window))
```

Placement is load-bearing and there is a test for it: put it below that return
and the one state the guard exists for — an empty tape — is the one state it
never stamps.

It issues **no query**. `LiquidationWindow` already carries `rows_total`, so
the guard rides free on a read the strategy had to do anyway. That matters on a
path that runs 57 times a cycle.

Three states, deliberately not two:

| window | stamp | why |
|---|---|---|
| `liquidation_table_missing` | `..._no_liquidation_table`, rows `None` | `rows_total` is a dataclass DEFAULT here, the query never ran. **Unknown, not zero.** |
| 0 rows | `..._deferred_empty_liquidation_tape`, rows `0` | we read it and it is empty |
| >= 1 row, even stale | `kill_clock_running` | see below |

**Staleness does NOT rewind the clock,** and that is a judgement call worth
Raven's eye. The ruling is ">= 1 row **to date**", not ">= 1 row right now". A
recorder that ran a week and died has produced evidence. If an outage rewound
the clock, the clause could never fire on a strategy whose feed is merely
unreliable — the guard would be un-expirable.

### The design choice that paid off within the hour

**`low_sample` is DERIVED from `n`, never asserted per asset.** Raven's
instruction named SOL. The 220-window data said BTC was thinner still (n=75 vs
SOL's 84) and only ETH cleared the bar (n=106). Hardcoding "SOL is the low-sample
one" would have shipped that error.

Then, mid-session, a concurrent session **re-measured at 500 windows** and
replaced the constants. Because the flag is computed, it cleared itself with no
second edit:

| asset | 220w rate / n | 500w rate / n | low_sample |
|---|---|---|---|
| BTC | 2.7% / 75 | **5.1% / 175** | True -> False |
| ETH | 6.6% / 106 | **9.3% / 248** | False |
| SOL | 14.3% / 196 | **15.8% / 196** | True -> False |

**Every rate moved UP at the larger sample and BTC nearly doubled.** The 220w
read was the optimistic end of sampling noise. Worth Raven's attention: ETH
*cleared* n=100 at 220 windows and still moved 6.6% -> 9.3%. Clearing convention
7's bar is necessary, not sufficient.

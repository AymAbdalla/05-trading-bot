## Task 0 (blocking precondition): RESOLVED, and not by this session

The handoff required finding whether the exit path reads `positions.stop_px`
(0.00 on all 67 `stop_too_tight` fair-value rows the critic flagged) or a
different field, before any change to the exit path could be interpreted.

**Finding.** `FairValueArb.manage_exit` (`strategies/polymarket/
fair_value_arb.py:811-813`) computes the discretionary stop LIVE on every
check - `self.stop_price_for(entry, outcome_side)` ->
`strategies.polymarket.base.tiered_stop_price` - compared against the book's
live best bid. It never reads `positions.stop_px`. That DB column is written
separately, for record-keeping only, by `ShadowStore.record_entry`
(`engine/polymarket/shadow_loop.py:844-868`) via `_entry_stop_px`
(`engine/polymarket/shadow_loop.py:2270-2300`), which calls the same
`stop_price_for` method at entry time and stores the result.

**The two facts are not in tension - they are two eras of the same column.**
`record_entry`'s own docstring says the column "used to be hardcoded to 0.00
for every Polymarket row." Commit `ea30111` (2026-08-18 16:22 EDT, "D-312 to
D-315: wire the general binary market spaces, register proposal 024") is
where `_entry_stop_px` and the tiered stop both landed - already on `main`
before this proposal was written. The 67 flagged trades predate that commit:
their rows were written under the old hardcoded-0.00 path, and their LIVE
exits at the time ran a flat `entry - 0.03` stop (`fair_value_arb.py:144-157`
documents the change), not the tiered rule that exists now and not the value
the DB column claims. `stop_px = 0.00` on those 67 rows is a bookkeeping gap
already closed for every row written since - not evidence the live exit ran
with no stop at all.

**No new fix was required.** `ea30111` already did it, as an uncredited
byproduct of unrelated market-space wiring - its own commit message never
names the stop_px fix, which is why nothing in `DECISIONS.md` had formally
closed the question until this session. I logged **D-320** to close it and
to save a future session the same git-log trail.

**What remains genuinely open, and out of scope for D-320**: the
deterministic classifier's `model_miscalibrated` verdict and the critic's
`stop_too_tight` verdict on the fair-value family are both still live. D-320
only establishes which field the exit path reads, not which verdict is
right. `PM_fair_value_settlement_exit` (below) is the experiment built to
decide between them, per the proposal's own framing.

## Task 1 + 2: the strategy, registered

`strategies/polymarket/fair_value_settlement_exit.py` -
`FairValueSettlementExit`, subclassing `FairValueArb` (the same shape
`FairValueArbInverse` uses: call the parent's `evaluate()` unchanged, only
post-filter the ENTER branch - reusing the model wholesale rather than
duplicating it). Registered in `strategies/polymarket/__init__.py` at
**appended index 24** (registry is now **25**). Declares
`supported_market_types = (MARKET_TYPE_CRYPTO_UPDOWN,)` only, narrower than
the parent's crypto+weather+general-binary (D-316) - this experiment is
scoped to "unchanged parent model on crypto Up/Down" per the proposal, not
the widened universe.

**What changed from the parent, and how:**

- `edge_threshold`: 0.04 -> **0.05** (proposal's rule 2, "a tighter gate, not
  a lower one"), passed straight through `super().__init__()`.
- **NEW gate**: entry ask <= **0.60** (`ENTRY_ASK_CAP`). The parent has no
  cap on the entry ask itself. Checked post-hoc against the side the parent
  already selected; skip reason `settlement_entry_ask_above_cap`.
- **NEW gate**: max **2** concurrent positions per instance
  (`MAX_CONCURRENT_POSITIONS`), tracked in `self._open` keyed on
  `(market_slug, attempt_number)` - NOT slug alone. I built this slug-only
  first and it was wrong: the parent's own `max_trades_per_window` allows up
  to 3 entry attempts inside ONE 5-minute window against the SAME slug, and a
  slug-only key let a second attempt silently overwrite the first's tracking
  entry, undercounting real concurrency. Caught by my own test
  (`test_max_two_concurrent_then_third_is_capped` initially failed with a
  wrong assumption about cross-window overlap, which does not exist for a
  hold-to-resolution single-window strategy - see below). Reuses the
  existing `strategy_concurrency_cap_reached` classification key rather than
  inventing a new one.
- **Exit A (primary)**: hold to resolution. `manage_exit` is a full rewrite
  (does not call `super().manage_exit()`) - no `converged`, `model_stop`,
  `time_stop` or `window_close`. `estimate()` is still inherited (this
  strategy still publishes a real fair value, unlike the inverse variant,
  which had to withhold it) but nothing reads it as a gate; it lands on
  every exit row as `fair_value_observed_not_acted_on`.
- **Exit B**: flat salvage floor at 0.10 (`SALVAGE_FLOOR`) - sell at
  whatever the bid pays (`URGENT_SELL_LIMIT`) if the bid is at or below it.
  **Degenerate case, handled**: `min_fair_value=0.10` is inherited unchanged
  and `edge_threshold=0.05`, so an entry can legally land near 0.05-0.09 -
  BELOW the flat floor. A flat 0.10 "stop" above a 0.06 entry would fire
  immediately, which is not a stop (convention 8). `salvage_stop_price()`
  collapses onto the structural 0.00 floor in that band and flags it
  (`salvage_floor_is_structural_floor=True`), the identical shape
  `tiered_stop_price` uses for its own degenerate band
  (`strategies/polymarket/base.py:611-619`). This is a reading of the
  proposal's flat number, not a deviation from it - the proposal never
  priced its floor against `min_fair_value`, and reproducing the exact
  `stop_too_tight` defect this exit exists to fix was judged worse than
  naming the exception.

**A discrepancy I found and did not act on**: the proposal's own
`data_requirements` field says position holding "has never been exercised at
15-minute holds for this family and should be smoke tested." `PM_fair_
value_arb` (this strategy's parent) trades the **5-minute** crypto Up/Down
window (`WINDOW_SECONDS = 300`), not a 15-minute one - the 15-minute
language matches proposal 032's family, not this one. Reads like a Forge
templating artifact (proposal 032 and 034 both came out of the same session,
per `strategies/proposals/forge_runs.jsonl`), not a considered claim about
this strategy. I did not correct the proposal document itself; flagging it
here so nobody scores a 15-minute hold requirement against a 5-minute
strategy. The actual holding-across-cycles mechanic (positions carried
across many `evaluate()` calls, `_open` pruned by estimated resolve time) IS
now covered - see Task 3 and "Smoke test" below.

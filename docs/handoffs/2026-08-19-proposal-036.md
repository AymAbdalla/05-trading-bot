## How the key is populated (Task 1)

`DipArb.observe(ctx)` already loops `ctx.market.outcomes` once per cycle to
write each side's tape row. For a two-outcome market that loop already holds
both token ids in hand - Gamma pairs `clobTokenIds` positionally with
`outcomes` (`engine/polymarket/markets.py:110-139`), so `outcomes[0]` and
`outcomes[1]` on one `Market` object ARE the complement pair, by
construction, before any tape write happens. So `complement_id` is read
directly off the sibling `Outcome` in the same `Market.outcomes` tuple - no
lookup call, no network round trip, matching data_requirements rule 2's
explicit ban on turning a tape write into a fetch. `condition_id` is
`ctx.market.condition_id`, likewise already in memory.

A market with other than two outcomes gets `condition_id` but
`complement_id = NULL` - there is no single complement to name. Historical
rows predate both columns and stay NULL, undocumented as anything but NULL
(proposal rule 3: no backfill, no invented mapping).

## Where I deviated from proposal 036's stated design, and why I kept the deviation

**The proposal's rule 1 and rule 4 specify three columns
(`condition_id`, `outcome_index`, `outcome_name`) and derive the complement
IN SQL from matching `condition_id` + `ts` + differing `outcome_index` -
explicitly rejecting a stored `complement_id` column: "Storing a
complement_token_id column instead would create a second place the truth
lives and a second place it can go stale."**

Your handoff instructions said something different: "Add a complement
lookup (token_id -> complement token_id via condition_id) to the tape write
path, stamped as `complement_id` on the row." I built what the handoff
said, not what the proposal said, on the read that the handoff is your
revision of the proposal's design, not a paraphrase of it. I did not
silently reconcile the two - flagging it here instead.

My defense if you intended the proposal's original shape: `complement_id`
here is not a second source of truth in the sense the proposal warns
about. It is written in the SAME `observe()` call, from the SAME `Market`
object, at the SAME instant as `condition_id` - never updated, never
re-derived, never looked up later. The staleness risk the proposal names
applies to a foreign-key-style column maintained across writes; this one is
computed once and is immutable per row, same as `outcome_index` would have
been. But it IS still redundant with what `condition_id` + `ts` + a
positional index would let you derive in SQL, and if you want the
proposal's exact three-column shape instead, it's a small follow-up: add
`outcome_index`/`outcome_name`, keep `complement_id` or drop it, your call.
I did not build a fallback matcher either way - both shapes are equally
"zero heuristic," just different storage.

## A bug I found and fixed before it could take the loop down (not asked for, but load-bearing)

`CREATE TABLE IF NOT EXISTS market_tape` in both `SCHEMA_SQL` copies is a
**no-op** against a `market_tape` table that already exists on disk - and it
already exists, in `db/trading.db` and `db/trading-survivors.db`, built by
the pre-036 schema (`id, market_id, ts, mid, best_bid, best_ask, source`,
verified live via `PRAGMA table_info`). Column additions alone would have
been silently swallowed, same shape as D-329's `fill_was_maker` dark-column
problem CLAUDE.md already documents.

But this one is worse than silent: `db/schema.sql` also declares
`CREATE INDEX idx_market_tape_condition_ts ON market_tape(condition_id, ts)`,
and `CREATE INDEX` against a column that does not exist is **not** a no-op -
it's `OperationalError: no such column: condition_id`. `ShadowStore.
ensure_schema()` replays `db/schema.sql` verbatim on every process start.
**Unmigrated, the very next restart - the one this handoff exists to
enable - would have crashed the loop at startup**, not silently skipped the
new columns.

Fixed the same way `_migrate_positions_pair_linkage_columns` /
`_migrate_positions_fill_provenance_column` already fix the identical
problem for `positions`: `_migrate_market_tape_complement_columns` runs
`PRAGMA table_info` + `ALTER TABLE ADD COLUMN` for anything missing, called
BEFORE `executescript`, in both `ShadowStore.ensure_schema()` (the loop's
own path) and `PriceTapeByToken._ensure_conn()` (DipArb's independent
bootstrap copy - it has always run its own `executescript(SCHEMA_SQL)`
against `self.db_path`, so it needed the identical fix or the off-crypto
tape write path would crash on first persisted write after this lands).

Verified against a throwaway copy of `db/trading.db` (never the live file):
`ShadowStore(db_path=<copy>)` migrates cleanly, columns land, no exception.
Copy deleted after.

## Task 2: the verification harness

`agents/forge_complement_check.py`. `complement_pairs(conn, since_ts=None)`
finds synchronous pairs by an EXACT key self-join only -
`a.condition_id = b.condition_id AND a.ts = b.ts AND a.complement_id =
b.market_id AND b.complement_id = a.market_id` - both directions required,
so a one-sided or corrupt `complement_id` can never surface as a pair. No
price is read until after a pair is already established by key.

`evaluate()` returns:
- `'unreadable'` - DB unreadable (convention 11, not an empty ok)
- `'failed_null_threshold'` - >5% of tape rows (after `since_ts`) carry NULL
  `condition_id`. Checked BEFORE the pair-count floor, so a tiny AND
  majority-NULL sample reports the failure rather than falling through to
  `insufficient_data` and hiding it. The note names the fix as REVERT,
  per the kill condition - the code does not revert anything itself.
- `'insufficient_data'` - fewer than `min_pairs` (default 1000) synchronous
  pairs yet. Convention 11: not a negative result.
- `'ok'` - reports `no_arbitrage_distribution` (mean/min/max/below_one
  count of `ask_a + ask_b`) and `ambiguity_fraction` (0.000 by
  construction - computed, not hardcoded, so a future join bug would trip
  it instead of silently reading 0).

**Could not demonstrate n >= 1000 today.** `db/trading.db`'s `market_tape`
has zero rows with the new columns, because the running loop is still on
commit `e033078` (pre-036) - exactly the state you told me not to change.
Ran it against the live db read-only to confirm this: `status:
'unreadable'` right now, because the columns are entirely absent from the
live table (expected - the migration above hasn't run yet, since nothing
has restarted). Confirmed via a throwaway copy that once the migration
DOES run, `evaluate()` reads correctly.

## What was skipped or deferred

  documented in both schema comments as "not keyed," not "no complement."
- **Task 2's success condition (1,000+ pairs, 0.000 ambiguity) is unverified

  The harness is built and tested against synthetic data; the live
  measurement waits for the next natural restart.

  not added. See the deviation section above.
- Rule 5 of the proposal (assert both asks present, count and report
  discards) is partially covered: `sum_distribution()` counts
  `missing_ask` separately from the sum distribution, but I did not
  separately break down `source='ask'`-only rows the way rule 5 describes -
  that distinction isn't visible to `forge_complement_check.py` without
  reading `source` per pair, which it doesn't currently do. Small addition
  if you want it before the first real run.
